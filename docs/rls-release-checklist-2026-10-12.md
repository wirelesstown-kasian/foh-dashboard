# RLS 업데이트 검증·배포 체크리스트

목표 배포일: 2026-10-12 월요일 (America/Chicago)

작성일: 2026-10-09. 이 문서는 검증 계획이며, 아래 항목은 아직 완료 처리하지 않았습니다. 체크리스트 작성으로 push·배포·DB 변경을 실행하지 않습니다.

이번 업데이트는 기존 운영 DB의 접근 권한을 변경합니다. 운영 데이터를 새 DB로 이전하는 작업이 아닙니다. 별도 테스트 DB는 검증용이며, 테스트 결과나 테스트 데이터를 운영 DB로 합치지 않습니다.

## 1. 검증 준비 — Codex + James

- [ ] 검증할 코드의 커밋/버전을 기록하고, RLS 변경과 관련 없는 로컬 변경을 분리한다.
- [ ] 새 앱이 별도 테스트 DB를 사용하도록 설정하고, 운영 DB와 다른 프로젝트인지 확인한다. 읽기·쓰기·사진 저장 경로 모두 확인한다.
- [ ] 테스트 DB에 검토된 스키마와 테스트 데이터를 준비한다. 로컬/운영 migration history가 다르므로 전체 migration을 무조건 재실행하지 않는다.
- [ ] 테스트용 manager, staff A(server), staff B, 권한이 다른 부서 직원, 비활성 직원의 과거 기록을 준비한다. 비활성 계정은 로그인에 사용할 수 없어야 한다.
- [ ] 메일은 테스트 수신처/대체 전송기로, Sheets는 테스트 문서로 연결한다. 예약 메일·주간 요약·리뷰 동기화·사진 정리 작업도 운영 대상을 사용하지 않는지 확인한다.
- [ ] 동일한 데이터·기간의 기존 정상 결과를 비교 기준으로 기록한다: EOD 총액, 직원별 tips, 승인 근무시간, wages/payroll, cash balance, 과거 월별/연간 총액.
- [ ] 앱의 서버 전용 자격증명과 세션 설정이 검증 환경에 존재하는지 확인한다. 비밀값은 체크리스트·스크린샷·로그에 기록하지 않는다.
- [ ] 테스트 DB에 RLS migration을 적용한 상태로 아래 수동 검증을 진행한다. 권한 변경 전의 테스트만으로 완료 처리하지 않는다.

## 2. 자동 테스트·빌드 — Codex

실행 직전에 설치된 Next.js 가이드를 확인한다. 각 명령의 결과와 경고를 기록한다.

- [ ] `node --test tests/*.test.mjs` — 세션 서명/만료, 권한 제한, 브라우저 요청 경로, 기존 집계 테스트 통과.
- [ ] `npx --no-install tsc --noEmit` — 타입 검사 통과.
- [ ] `npm run lint` — 오류 없음. 경고는 내용과 영향을 확인.
- [ ] `npm run build` — 프로덕션 빌드 성공.
- [ ] 실행할 검증 앱이 위에서 확인한 코드 버전인지 확인.

자동 검사 결과는 실제 staff 업무, DB 권한, 메일/Sheets 연동의 완료 증거를 대신하지 않는다.

## 3. 실제 화면 검증 — James

Manager와 staff는 서로 다른 브라우저 프로필 또는 일반/시크릿 창을 사용한다. 저장 확인은 화면 알림뿐 아니라 새로고침 또는 재로그인 후 값이 남는지까지 확인한다. 변경·삭제·지급·발송은 테스트 환경에서만 진행한다.

### 로그인·권한

- [ ] Manager 로그인 → 관리자 화면/리포트 진입 → 로그아웃 → 다시 로그인 정상.
- [ ] Staff A/B 각각 로그인 가능. 잘못된 비밀번호/PIN은 거부되고, 비활성 계정은 로그인 불가.
- [ ] Staff가 관리자 URL을 직접 열어도 인사·급여·설정 수정과 관리자 재설정 작업을 실행할 수 없음.
- [ ] Staff에게 다른 직원의 급여·주소·로그인 자격정보가 노출되지 않음. 허용된 팀 스케줄/공유 task 상태는 정상 표시.
- [ ] Manager 인증이 필요한 작업은 유효한 manager 인증 후에만 성공. 일반 staff PIN으로 관리자 작업을 할 수 없음.

### 출퇴근·tasks·오픈

- [ ] 테스트 직원의 PIN으로 clock-in → break 시작/종료 → clock-out 정상. 기록의 직원·시간·휴게시간이 정확함.
- [ ] 잘못된 PIN이나 허용되지 않은 상태 전환은 거부됨. 다른 직원 기록으로 잘못 저장되지 않음.
- [ ] 출퇴근 사진 저장/조회 정상. Manager 승인·시간 수정 결과가 clock records와 wages에 반영됨.
- [ ] Task 완료 → 새로고침 → 완료 상태/직원/포인트 유지. 취소·재완료 시 중복 포인트 없음.
- [ ] 출근 조건과 task 단계 전환이 기존 업무 규칙대로 동작. Manager reset/수정도 정상.
- [ ] Server 직원의 register open에서 opening cash·오픈 담당자·단계가 저장됨. 실제 매장에서 오픈하는 다른 역할이 있다면 그 역할도 필요한 권한을 갖는지 확인.

### EOD·tips

- [ ] 실제 마감 담당 역할로 오늘 영업일의 EOD 입력·저장 정상. 마감 담당자와 날짜가 정확함.
- [ ] 현금·카드·매출·세금·cash deposit·차액이 비교 기준과 맞고, 저장 후 다시 열어도 동일함.
- [ ] 직원별 근무시간·tip share·house deduction·net tip과 전체 합계가 비교 기준과 맞음.
- [ ] EOD 수정·재저장 또는 tip 재계산 후 중복/누락 없이 전체 tip pool이 유지됨.
- [ ] Manager가 과거 EOD/tips를 조회·수정 가능. 일반 staff는 허용되지 않은 과거 보고서나 타인 마감 기록을 수정할 수 없음.
- [ ] 실패·재시도 시 EOD만 저장되고 tips가 빠지는 등 부분 저장이 없는지 확인. 문제가 있으면 배포 보류.

### Schedule·staffing

- [ ] Manager가 draft 생성/복사/수정 → 게시 → 새로고침 후 일정·부서·직원 순서 유지.
- [ ] Staff는 게시된 팀 스케줄을 정상 조회하고, 미게시 shift의 상세 내용은 볼 수 없음.
- [ ] 테스트 직원의 역할·부서·급여·활성 상태 변경 후 schedule, tips, wages, clock records, tasks, EOD, reporting 및 API/email 출력 영향을 함께 확인.
- [ ] 역할/부서가 바뀌거나 비활성화된 직원의 기존 근무·tips·급여·보고서 기록이 남고, 필요한 과거 집계에 포함됨.
- [ ] Manager에서 staff로 변경하거나 비활성화한 테스트 계정의 기존 세션으로 관리자 작업을 계속할 수 없음.

### Wages·payroll·reporting

- [ ] 승인 근무시간·휴게시간·시급·보장급·commission이 wages/worksheet에서 비교 기준과 일치.
- [ ] 테스트 payroll 생성·수정 후 지급 항목, 현금/체크 배분, tips 및 cash balance가 일치. 재시도 시 중복 지급 기록 없음.
- [ ] Clock records, EOD history, wages, payroll payouts, task/reward 보고서의 조회·필터 정상.
- [ ] 월별/연간 dashboard의 매출·급여·tips 합계와 기존 imported totals가 비교 기준과 일치.
- [ ] Review board, leaderboard, reward 목록/조정/사용 흐름이 권한에 맞게 동작하고 포인트가 중복되지 않음.
- [ ] Announcements와 매장 설정이 필요한 화면에 표시되고, 설정 수정은 manager만 가능.

## 4. API·DB·연동 검증 — Codex

- [ ] 로그인 없음/위조/만료 세션으로 보호된 API 요청이 거부됨. 실패 요청이 데이터를 변경하거나 메일/Sheets 작업을 실행하지 않음.
- [ ] Staff A가 staff B의 ID, 과거 영업일 또는 허용되지 않은 필드를 보내도 조회·수정 권한을 우회할 수 없음.
- [ ] 브라우저는 승인된 서버 경로로 테이블 읽기/쓰기를 수행. 서버 비밀키·PIN hash·password hash가 응답/번들에 포함되지 않음.
- [ ] 테스트 DB에서 20개 public 테이블의 RLS와 `anon`/`authenticated`/`PUBLIC` 및 column grants를 확인. [검증 SQL](rls-cutover-verification.sql) 활용.
- [ ] 모든 해당 테이블에서 client 역할의 직접 SELECT/INSERT/UPDATE/DELETE가 차단됨. 쓰기 차단 실험은 테스트 데이터에만 수행.
- [ ] 승인된 서버 경로의 정상 읽기/쓰기도 확인. 차단 결과나 빈 배열만으로 검증 완료 처리하지 않음.
- [ ] 출퇴근 사진은 허용된 직원/manager가 조회 가능하고, 익명·무관한 직원의 조회는 거부됨.
- [ ] EOD/schedule/wage/payroll/performance/weekly-summary 메일을 테스트 수신처에서 확인. UI와 날짜·금액·직원·부서가 일치.
- [ ] EOD/clock records/wage/payroll/cash balance Sheets sync가 테스트 문서에 정확히 반영됨.
- [ ] 예약 schedule 메일의 발송/취소/발송 상태와 재시도 시 중복 방지 확인. Cron 인증과 리뷰 sync/사진 cleanup도 테스트 대상에서 확인.
- [ ] SQL inventory/grants 확인 및 Supabase advisors의 관련 보안 항목 재검토. 오류가 없는 로그만으로 권한 검증을 대체하지 않음.

## 5. 배포·복구 준비 — Codex + James

- [ ] 모든 필수 항목 통과. 확인 못 한 항목은 통과로 처리하지 않고 사유/영향 기록.
- [ ] 운영 DB의 schema·grants·default privileges·policies 스냅샷과 데이터 백업/복구 경로 확인.
- [ ] 현재 production 배포 ID와 새 앱의 코드 버전·대상 프로젝트·환경 기록.
- [ ] RLS 적용 후에도 정상 동작하는 복구용 앱을 별도 확보하고 검증. 현재 구버전으로 Vercel 롤백만 하면 직접 DB 접근이 막힐 수 있음.
- [ ] 복구용 앱의 세션 설정/서버 자격증명도 운영 RLS와 호환되는지 확인. 불필요한 RLS 해제나 익명 쓰기 권한 복원을 기본 복구 방법으로 삼지 않음.
- [ ] James의 명시적 push/배포 지시 후 새 앱 배포 → 운영 읽기/인증 확인 → 검토된 RLS cutover 적용 → 정상 접근/직접 접근 차단 재확인 순서로 진행.
- [ ] 전체 `supabase db push`를 실행하지 않음. 기존 migration history 불일치가 있으므로 검토된 cutover만 지정한 절차로 적용.
- [ ] 기존 열린 탭에 새로고침/재로그인 안내. 배포 후 다음 실제 clock/task/EOD 흐름, 예약 작업, 권한 오류 및 업무 총액 확인.

RLS 적용 전에 실패하면 DB 변경을 진행하지 않는다. RLS 적용 후 실패하면 검증된 호환 앱으로 복구하거나 해당 서버 경로를 수정한다. Vercel 롤백은 DB 권한이나 그동안 저장된 데이터를 이전 시점으로 복원하지 않는다.
